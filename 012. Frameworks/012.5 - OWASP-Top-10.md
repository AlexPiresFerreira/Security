## 📌 Visão geral

O **OWASP Top 10** é um documento de conscientização sobre riscos importantes à segurança de aplicações web. É um bom ponto de partida para estudar AppSec, mas **não é uma lista completa de vulnerabilidades nem substitui um processo de avaliação de segurança**.

- **Projeto oficial:** [OWASP Top 10](https://owasp.org/www-project-top-ten/)
- **Versão mais recente publicada:** OWASP Top 10 2025
- **Versão detalhada nesta nota:** OWASP Top 10 2021

> **Nota de versão:** esta nota mantém a edição 2021 como referência de estudo porque seu conteúdo está detalhado abaixo. Consulte a publicação oficial para estudar a estrutura e as categorias da edição 2025. A numeração e os nomes das categorias podem mudar entre edições.

### Como usar esta nota

Para cada risco, procure entender:

1. **Causa:** que falha de projeto, implementação ou configuração permite o problema?
2. **Impacto:** que dados, funções ou sistemas podem ser afetados?
3. **Prevenção:** quais controles reduzem a probabilidade ou o impacto?
4. **Detecção:** que logs, testes ou sinais podem revelar a falha?

## A01:2021 — Falhas de controle de acesso

### O que é

Ocorre quando uma pessoa consegue acessar dados ou executar ações além das permissões que deveria ter. A autorização deve ser verificada **no servidor**, em cada operação protegida.

### Exemplos

#### IDOR / BOLA

Um identificador de objeto não é uma autorização. Alterar o ID de um recurso não deveria permitir acesso aos dados de outra pessoa.

```text
GET /api/profiles/123
```

A aplicação deve verificar se o usuário autenticado tem permissão para acessar o perfil `123`, independentemente de o identificador ser previsível ou difícil de adivinhar.

#### Elevação de privilégio por dados controlados pelo cliente

Não confie em campos recebidos do navegador, como `is_admin`, `role` ou `owner_id`, para decidir permissões. Esses valores devem ser determinados ou validados pelo servidor.

### Prevenção

- Negar acesso por padrão e conceder somente as permissões necessárias.
- Validar autorização no servidor em **cada requisição**.
- Aplicar autorização no nível do objeto e da função, não apenas esconder botões na interface.
- Usar RBAC ou ABAC quando apropriado.
- Evitar confiar em IDs, papéis ou flags enviados pelo cliente.
- Registrar e revisar tentativas de acesso negado, sem expor dados sensíveis nos logs.
- Testar acesso horizontal (usuário para usuário) e vertical (usuário comum para administrador).

> **Atenção:** `basename()` pode remover componentes de caminho, mas não substitui autorização, mapeamento de arquivos permitidos e validação segura do caminho final.

## A02:2021 — Falhas criptográficas

### O que é

Falhas no uso, na configuração ou na ausência de criptografia podem expor dados sensíveis. A proteção necessária depende da sensibilidade dos dados e do cenário de ameaça.

### Exemplos

- Transmitir credenciais por HTTP sem TLS.
- Armazenar senhas em texto claro ou usando hash rápido, como MD5 ou SHA-1.
- Usar criptografia, protocolos ou parâmetros obsoletos.
- Expor chaves, tokens ou segredos em código-fonte, logs ou repositórios.
- Não proteger dados sensíveis armazenados ou em trânsito.

### Prevenção

- Usar HTTPS com configuração TLS atualizada.
- Armazenar senhas com algoritmos próprios para senhas, como Argon2id, bcrypt ou scrypt, configurados conforme as recomendações atuais.
- Não usar criptografia reversível para armazenar senhas.
- Usar bibliotecas criptográficas reconhecidas; evitar criar algoritmos próprios.
- Proteger, rotacionar e controlar o acesso a chaves e segredos.
- Definir quais dados realmente precisam ser armazenados e por quanto tempo.
- Avaliar configuração, certificados, protocolos e cifras com ferramentas apropriadas.

> **Esclarecimento:** hashes de senha não são criptografia reversível. Também não se deve tratar uma lista fixa de algoritmos ou tamanhos de chave como recomendação universal; a escolha depende do uso, da biblioteca e dos padrões atuais.

## A03:2021 — Injeção

### O que é

A injeção ocorre quando dados não confiáveis são interpretados como parte de uma consulta ou comando. Pode afetar bancos de dados, sistemas operacionais, mecanismos de busca, interpretadores e outros componentes.

### SQL Injection

**Padrão vulnerável:** concatenar diretamente a entrada do usuário em uma consulta SQL.

```php
// Exemplo vulnerável: não concatenar entrada na consulta.
$query = "SELECT * FROM users WHERE username = '$username'";
```

**Mitigação:** usar consultas parametrizadas. O exemplo é ilustrativo; a sintaxe exata depende da biblioteca e do driver.

```php
$stmt = $conn->prepare(
    "SELECT id, username FROM users WHERE username = ?"
);
$stmt->bind_param("s", $username);
$stmt->execute();
```

Consultas parametrizadas separam os dados da estrutura da consulta. Escape manual, filtros improvisados e listas de bloqueio não são substitutos confiáveis.

### Command Injection

Evite chamar o shell com uma string construída a partir de entrada do usuário.

```python
# Padrão perigoso:
# os.system(f"comando {valor_recebido}")
```

**Preferência:** não executar comandos do sistema quando a tarefa puder ser feita por uma biblioteca. Se a execução for indispensável, use uma API que receba argumentos separados, valide os valores por lista permitida e evite o shell.

### Outras formas de injeção

- **XSS:** entrada é interpretada como conteúdo executável pelo navegador.
- **LDAP injection:** entrada altera filtros ou consultas LDAP.
- **OS command injection:** entrada altera comandos do sistema operacional.
- **Template injection:** entrada é interpretada por um mecanismo de templates.

### Prevenção

- Usar consultas parametrizadas e APIs seguras.
- Validar a entrada conforme o tipo e a finalidade esperados.
- Codificar a saída de acordo com o contexto: HTML, atributo, JavaScript, URL etc.
- Evitar construir comandos, consultas ou templates por concatenação.
- Aplicar menor privilégio às contas de banco e de sistema.
- Não considerar WAF ou sanitização genérica como correção da causa raiz.

## A04:2021 — Projeto inseguro

### O que é

Risco decorrente de requisitos, decisões de arquitetura ou fluxos de negócio que não consideram adequadamente ameaças e controles de segurança. Uma implementação correta não corrige, por si só, um desenho inseguro.

### Exemplos

- Fluxo de recuperação de conta que permite tomar o controle da conta sem verificação adequada.
- Processo de compra que confia em preço ou quantidade enviados pelo cliente.
- Falta de limites de negócio que permita abuso automatizado de uma função.
- Ausência de requisitos de autorização ou proteção de dados no projeto.

### Prevenção

- Definir requisitos de segurança e privacidade desde o início.
- Modelar ameaças para funções e dados importantes.
- Mapear fluxos de confiança, ativos, atores e limites do sistema.
- Criar regras de negócio verificadas no servidor.
- Estabelecer controles contra abuso, como limites e validações proporcionais ao risco.
- Fazer revisões de arquitetura e testes de segurança durante o desenvolvimento.

## A05:2021 — Configuração de segurança incorreta

### O que é

Configurações inseguras ou incompletas podem expor funcionalidades, informações ou serviços. O risco pode estar na aplicação, no servidor, na nuvem, no banco de dados ou em componentes de rede.

### Exemplos

- Credenciais ou configurações padrão mantidas em produção.
- Mensagens de erro que revelam detalhes internos.
- Serviços, portas, páginas de diagnóstico ou recursos desnecessários expostos.
- Cabeçalhos de segurança ausentes ou configurados incorretamente.
- Permissões excessivas em arquivos, buckets ou serviços de nuvem.

### Prevenção

- Usar configurações seguras por padrão e ambientes padronizados.
- Remover ou desabilitar recursos, contas e serviços desnecessários.
- Manter segredos fora do código-fonte.
- Aplicar menor privilégio em identidades, contas de serviço e recursos de nuvem.
- Evitar expor mensagens internas de erro ao usuário; registrar detalhes de forma segura.
- Revisar configurações em desenvolvimento, homologação e produção.
- Automatizar verificações de configuração e detectar desvios.

## A06:2021 — Componentes vulneráveis e desatualizados

### O que é

Aplicações dependem de bibliotecas, frameworks, serviços e componentes. Componentes sem suporte ou vulneráveis podem introduzir riscos, especialmente quando a organização não sabe onde são usados ou não consegue atualizá-los.

### Prevenção

- Manter inventário de componentes e versões; um SBOM pode ajudar.
- Monitorar avisos de segurança e vulnerabilidades aplicáveis ao ambiente.
- Atualizar dependências e remover as que não são utilizadas.
- Fixar e revisar versões conforme o processo de desenvolvimento.
- Usar fontes confiáveis e proteger o processo de aquisição de dependências.
- Avaliar impacto e exposição antes de priorizar correções.
- Usar ferramentas de análise de dependências como apoio, não como substituto da revisão.

> **Atenção:** uma ferramenta pode reportar vulnerabilidade sem que ela seja explorável no contexto da aplicação, ou não detectar um componente vulnerável. Confirme versão, configuração, uso e exposição antes de concluir.

## A07:2021 — Falhas de identificação e autenticação

### O que é

Falhas nos processos de login, autenticação multifator, recuperação de conta ou gerenciamento de sessão podem permitir que terceiros se façam passar por usuários legítimos.

### Exemplos

- Ausência de proteção contra tentativas automatizadas de login.
- Recuperação de conta fraca ou previsível.
- Sessões não invalidadas após logout ou mudança de senha.
- Identificadores de sessão reutilizados depois da autenticação.
- Tokens ou identificadores de sessão expostos em URLs.

### Prevenção

- Oferecer MFA, especialmente para contas privilegiadas e operações sensíveis.
- Usar fluxos seguros de recuperação e mudança de senha.
- Limitar tentativas e detectar padrões automatizados sem criar bloqueios fáceis de abusar.
- Gerar identificadores de sessão imprevisíveis e renová-los após autenticação ou mudança de privilégio.
- Invalidar sessões no logout e em eventos que exijam reautenticação.
- Usar cookies de sessão com atributos adequados, como `Secure`, `HttpOnly` e `SameSite`, conforme o contexto.
- Evitar mensagens de login que revelem desnecessariamente se uma conta existe.

> **Senhas:** priorize senhas longas, comparação com listas de senhas comprometidas, armazenamento seguro e MFA. Exigir combinações rígidas de maiúsculas, números e símbolos pode incentivar padrões previsíveis; siga orientações atuais de identidade digital.

## A08:2021 — Falhas de integridade de software e dados

### O que é

Ocorre quando código, atualizações ou dados críticos são aceitos sem verificar adequadamente sua origem e integridade. Pode envolver pipelines de CI/CD, bibliotecas, atualizações e desserialização.

### Exemplos

- Instalar dependências sem revisão ou controle de origem.
- Pipeline de CI/CD com permissões excessivas ou segredos expostos.
- Processar dados serializados não confiáveis com mecanismos que podem executar código.
- Aceitar atualizações sem verificar assinatura ou origem.

### Prevenção

- Proteger repositórios, pipelines, credenciais e artefatos de build.
- Aplicar menor privilégio a contas e tokens do CI/CD.
- Revisar alterações e controlar aprovações de publicação.
- Verificar origem, assinatura e integridade de artefatos quando suportado.
- Inventariar dependências e acompanhar alterações.
- Evitar desserializar dados não confiáveis com mecanismos que permitam execução de código.

> **Atenção:** JSON é frequentemente preferível a formatos de serialização executáveis para dados simples, mas não é automaticamente seguro: ainda é necessário validar esquema, tamanho, tipos e conteúdo.

## A09:2021 — Falhas de logging e monitoramento de segurança

### O que é

Logs insuficientes, sem proteção ou sem monitoramento podem atrasar a detecção, dificultar a investigação e limitar a resposta a incidentes.

### Eventos que podem ser relevantes

- Autenticações bem-sucedidas e malsucedidas.
- Tentativas de acesso negado e falhas de autorização.
- Mudanças de privilégios e configurações importantes.
- Ações administrativas e operações sensíveis.
- Erros relevantes e sinais de abuso.

### Não registrar sem necessidade

- Senhas.
- Tokens de sessão, chaves ou segredos.
- Dados completos de pagamento.
- Dados pessoais ou sensíveis que não sejam necessários para a finalidade do log.

### Prevenção

- Definir quais eventos devem ser registrados e por quanto tempo.
- Sincronizar horários e centralizar logs quando apropriado.
- Restringir acesso e proteger a integridade dos registros.
- Criar alertas para eventos relevantes e investigar alertas.
- Sanitizar dados controlados pelo usuário para reduzir riscos de injeção de log.
- Testar se os eventos importantes realmente chegam ao sistema de monitoramento.
- Estabelecer processo de resposta e retenção compatível com requisitos legais e operacionais.

## A10:2021 — Server-Side Request Forgery (SSRF)

### O que é

SSRF ocorre quando uma aplicação busca um recurso indicado, direta ou indiretamente, por uma entrada não confiável. O servidor pode acabar acessando sistemas internos ou serviços que não deveriam estar disponíveis por essa função.

### Cenários de risco

- Função que importa uma imagem a partir de uma URL enviada pelo usuário.
- Serviço que busca conteúdo remoto sem restringir destinos.
- Aplicação com acesso de rede a serviços internos ou metadados de nuvem.

### Prevenção

- Sempre que possível, aceitar identificadores ou destinos predefinidos em vez de URLs arbitrárias.
- Usar uma lista restrita de destinos permitidos e validar esquema, hostname e porta.
- Validar o endereço resolvido e impedir acesso a destinos não autorizados, incluindo endereços locais, privados, link-local e de metadados.
- Considerar redirecionamentos e mudanças de resolução DNS; validar o destino efetivo da conexão.
- Desabilitar esquemas de URL desnecessários e limitar protocolos aceitos.
- Restringir conexões de saída por firewall ou controles de rede.
- Aplicar limites de tempo, tamanho de resposta e tipos de conteúdo.

> **Atenção:** verificar apenas o texto do hostname ou bloquear alguns IPs conhecidos não é suficiente. Redirecionamentos, IPv6, DNS rebinding e diferenças entre validação e conexão podem contornar verificações simplistas.

## 🧪 Como estudar e testar

Use apenas aplicações próprias, ambientes de laboratório ou sistemas para os quais exista autorização explícita.

- **Revisão de código:** procure padrões perigosos e valide os controles no servidor.
- **Testes dinâmicos:** verifique comportamento e controles com ferramentas apropriadas.
- **Testes automatizados:** inclua verificações de segurança no ciclo de desenvolvimento.
- **Threat modeling:** avalie fluxos, ativos, atores e limites de confiança.
- **Validação manual:** confirme cada achado, seu impacto e as condições necessárias.

O resultado de uma ferramenta precisa ser interpretado. Uma detecção automática não comprova, sozinha, impacto explorável; ausência de alertas também não comprova segurança.
